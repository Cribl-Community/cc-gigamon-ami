# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"Gigamon Network Observability" — a **Cribl App Platform app**: a React + TypeScript + Vite SPA that runs inside the Cribl UI (a sandboxed iframe) as a network-observability dashboard. It runs **Cribl Search** (KQL) jobs against the Cribl Lake dataset `gigamon_ami` (Gigamon Application Metadata Intelligence flow records) and renders the results across a set of tabs.

Read **`AGENTS.md`** first — it is the authoritative Cribl App Platform developer guide (fetch proxy, KV store, `proxies.yml`/`policies.yml`, navigation, Capra UI rules, versioning). This file covers what's specific to *this* app.

## Commands

```bash
npm run dev             # Vite dev server on port 5173 (strict) — see dev proxy note below
npm run build           # tsc -b + vite build → dist/
npm test                # vitest run — the whole suite, once
npm run lint            # oxlint (config in .oxlintrc.json)
npm run queries:extract # regenerate src/queries/__frozen__/display.json from src/
npm run pack:samples    # regenerate the onboarding pack's synthetic samples + default/samples.yml
npm run pack:check      # samples reproduce byte for byte, and the pack validates
npm run pack:build      # write build/packs/cc-network-gigamon-ami-<version>.crbl (deterministic)
npm run pack:release-check # NETWORK: download the pinned pack release, compare its sha256 with PACK_SHA256
npm run assets:budget   # after a build: initial/lazy/total JS against asset-budget.json
npm run preview         # preview the production build
npm run package         # test + build + bundle into build/<name>-<version>.tgz (bumps version)
```

### The gates, and what each one catches

`.github/workflows/ci.yml` runs `npm run lint`, `npm run build`, `npm test`, `npm run pack:check`,
`npm run assets:budget` (after the rest, so an over-budget PR still shows them) and, last, the
network-dependent `npm run pack:release-check` on **every push and every pull request** — not only at release, because a reviewer needs them red before approving, not
weeks later at publish time. `npm run package` runs the suite *before* it writes the new version, so
a failing test can never leave a bumped `package.json` behind for someone to commit by accident.

## Runtime environments (critical)

The app runs in two modes, detected in `src/cribl/config.ts`:

- **Installed in Cribl** (`IS_INSTALLED`): `window.CRIBL_API_URL` is set and the platform fetch-proxy injects auth automatically. `API_BASE` = that URL.
- **`npm run dev`**: no platform globals. `API_BASE` = `/capi`, which `vite.config.ts` proxies to the real Cribl API, injecting an OAuth token fetched from the **gitignored `.dev/cribl.json`** client credentials. Without that file the dev proxy is inert (search calls will fail). The Cribl UI loads the dev server as `/?init=<workspace bridge script>`, and `vite.config.ts` injects that URL as a `<script src>`; which one is `scripts/devInitScript.ts`'s decision. A request carrying `?init=` gets exactly that init, remembered under the requesting page's origin (Referer, else Origin, else the init's own origin); a request without one — any reload once `App.tsx` has redirected `/` to `/flow-map` and dropped the query string — gets the init remembered for *its* origin; with an unknown origin it gets the one remembered init only while a single origin has ever been seen, and nothing once two have. An init that is not an absolute http(s) URL is never remembered or injected. *(Before 2026-09-24 the first workspace's init won forever, so a second workspace's Live Preview loaded the first one's bridge.)*

Just call `fetch()` normally — never handle auth. All API calls go through `${API_BASE}/...`, and
everything that is not Search goes through `src/cribl/capi.ts`.

**The app-scoped KV store does not work on the localhost dev page.** That proxy rewrites `/capi` →
`/api/v1` without the `/a/{appId}/` scope, and `__dev__<name>` is not a registered app, so every
`/kvstore/…` call 404s. Anything persistent is therefore verifiable only **installed**, or in the
in-UI Live Preview where the platform proxy adds the scope. `src/cribl/kv.ts` keeps a
session-lifetime shadow of refused writes so a developer isn't re-dismissing the same banner all
afternoon — it is not persistence, and `putDoc` answers `false` when only the shadow holds a value.

Key constants in `config.ts`: `SEARCH_GROUP = 'default_search'` (search **always** runs here), `LAKE_DATASET = 'gigamon_ami'`, `STREAM_GROUP = 'default'` (re-exported by `provision.ts` as `DEFAULT_STREAM_GROUP` — the worker group Guided Setup's picker starts on, not the only one it can write to). Deep-link helpers (`searchUiUrl`, `criblInvestigateUrl`, `criblUiUrl`) build root-relative links installed, and prefix `window.__CRIBL_SEARCH_ORIGIN` (dev-injected) in dev preview. `config.ts` also holds **one piece of state**, the dataset the app is reading (`activeDataset()`; only `src/cribl/datasetTarget.ts` calls `setActiveDataset`), and `searchUiUrl` and `criblInvestigateUrl` rewrite the query onto it with `toActiveDataset`, so a drill-down opens on the dataset the panel actually read. `LAKE_DATASET` is still `gigamon_ami`, and every query string in `src/queries/` still says so. *(Added 2026-09-24, with sample data.)*

## Architecture

**Data flow: KQL from `src/queries/` → job → poll → NDJSON rows → hook → tab.**

- `src/queries/<tab>.ts` — **every KQL string and query builder the app runs or shows.** They are
  not in the tab files. A panel's ⓘ shows the exact query behind its number, so the string *is* the
  provenance of the figure on screen; `scripts/extract-queries.mjs` regenerates
  `src/queries/__frozen__/display.json` from these modules and `display-freeze.test.ts` diffs it.
  Nothing here may import a `.tsx` or anything that reaches one (`../cribl/useSearch`, `../app/*`,
  `../components/*`), because the extractor loads these modules under plain Node. Static reference
  data that *generates* queries (`FINDINGS`, `TECHNIQUES`, `AI_APPS`) lives in `src/data/` for the
  same reason; the rest of `src/data/` is display reference (`amiFields`, `pqc`) and **client-side
  classifiers** (`SAAS_APPS`) — a list that appears in no query string but decides which rows land
  in a panel. The extractor's own word for why the third kind belongs here is the `catalogs` bucket:
  *"data that moves a number without ever appearing in a query string"*. **Export them as arrays,
  never as `Set`s** — the digest is `JSON.stringify(value)`, every `Set` stringifies to `"{}"`, so a
  `Set` here freezes to a constant that an empty one would also produce, and the gate is dead while
  still looking live. Build the `Set` in the tab, as `ShadowAi.tsx` does.
  *Corrected in PR #4 (2026-09-16). This section used to say each tab "define[s] KQL query constants
  at module scope".*
- `src/queries/stackIds.ts` — **the one list of Stream object ids the Data Flow counters name**
  (sources, pipelines, destinations, per stack and path). `METRICS_QUERY` and `LAKE_TOTAL_QUERY` in
  `src/queries/dataFlow.ts` are *built* from it, so a new onboarding stack is a new entry there,
  never an edit to a query string. The pack's ids are imported from `src/cribl/pack.ts`, and
  `stackIds.test.ts` holds the `<type>:` prefixes to the pack YAML and sums the queries' predicates
  over modelled `cribl_metrics` rows to show nothing is double-counted. **A pack's objects are named
  by their measured in-pack labels** (2026-09-25): input `<type>:<packId>.<id>`, output
  `cribl_lake:<packId>.<id>`, route `<packId>.<routeId>` (`packInputLabel`, `packOutputLabel`,
  `packRouteLabel` in `pack.ts`; `stackIds.test.ts` derives each from the pack YAML the same way). A
  pipeline's label inside a pack is **unmeasured** (no `pipe.*` row appeared for a test pack's
  pipeline), so no counter names a pack pipeline: every pack path is counted for Processing by its
  destination (`DESTINATION_COUNTED_PATHS`), and the test models pack `pipe.*` rows under a label no
  query could guess. *(Corrected 2026-09-25, `fix/pack-021-route-ids`: the pack paths used the
  global forms — `syslog:in_gno_syslog`, `cribl_lake:gigamon_ami_json_lake` — which no pack row
  carries, and 0.1.0's syslog path was counted by `pipe.out_events` on `gno_syslog`.)* `src_events` is
  `total.in_events` by `input` — the source's own intake, once per event however many routes take
  it — not `pipe.in_events` by `from_input`. `from_input` is added to a pipeline or destination term
  only where that object is on more than one path (`SHARED_PIPELINES` / `SHARED_OUTPUTS`), because
  whether a routed path's rows carry it is unmeasured. A path that shares its (source, pipeline)
  pair with another path — the pack's JSON + Parquet dual-write — is not counted by its pipeline at
  all either: `pipe.out_events` would count each event once per path, so its Processing figure is the
  destination's `total.out_events` (`DESTINATION_COUNTED_PATHS`); only the remaining global paths
  (`PIPELINE_COUNTED_PATHS`) use the pipeline's own counter. The Destinations plate and the Lake card count
  only destinations that write `gigamon_ami` (`COUNTED_OUTPUTS`), so a copy to another dataset is
  not counted. The queries count every stack listed:
  the demo DataGen (`running`), the older Guided Setup Syslog stack (`retired` — this release only
  offers to remove it, but a tenant that ran an earlier one may still be running it), Guided
  Setup's Raw HTTP stack (`offered`), pack 0.1.0 (`released`, from `PACK_0_1_0`), and `pack-0.2`,
  one stack for 0.2.0 and 0.2.1 because they ship the same ids, `released` since 0.2.0 is on
  `PACK_PUBLISHED_VERSIONS`. A 0.1.0 or 0.2.0 source can receive events its routes never match, so
  on those the Sources figure can run ahead of Processing and Destinations — which is the truth.
  *(Corrected 2026-09-25, `fix/pack-021-route-ids`: this said the queries counted "one no release
  has shipped", pack 0.2.0, `unreleased` while `PACK_PUBLISHED` was false.)* The ⓘ prose and stage headings name only stacks whose `status`
  is `running`, `offered` or `retired` (`SHOWN_*`). *(Corrected 2026-09-24. This said pack 0.1.0
  was `unreleased` and 0.2.0 `planned`, and that only `running` and `offered` are named.)* Because
  `gno_pipeline_c1h` runs `METRICS_QUERY` and `gno_lake_30d_c1d` can run `LAKE_TOTAL_QUERY`, a
  change to the list shows as drift on those schedules. *(Added 2026-09-24. Before it, the counters
  hard-coded the demo's objects.)*
- `src/cribl/search.ts` — the Search client. `runSearch(query, opts)` POSTs a job to `/m/default_search/search/jobs`, polls `/status` to completion, then reads `/results` (NDJSON: a header line with `totalEventCount`, then one JSON row per line). Retries 429/5xx with backoff. `q(pipeline)` prefixes `dataset="gigamon_ami"` onto a pipeline. `withExecPrefix` prefixes `set max_running_time_per_search=` from the cap tiers, scaled by the window the query reads — **execution only, never in an ⓘ**. It also prefixes `set allow_previous_results="2min"` (`REUSE_WINDOW`) when the caller passes `reuse` — measured 30.92 s → 0.95 s and zero billed on a repeat of the same query at the same relative range (A-SP21), matched on the *relative* range spec. It is off by default, and refused outright on a `$vt_results` read (A-D15), so a caller that submits a job to measure something still measures. Job status is polled on a ramp (`POLL_RAMP_MS`: 100 ms rising to a 1.5 s ceiling), not the flat 700 ms it used to be. A job the cap stops ends `failed` and surfaces as `SearchTimeLimitError`, which panels render as *Search stopped*; `cancelJob` stops an abandoned or over-running job on the server. `runFieldSummaries` uses the `/field-summaries` endpoint. **The job body is rewritten at submit onto the dataset the app is reading** (`toActiveDataset`; `q()` itself still writes `gigamon_ami`), so every panel, fallback and direct read follows the sample-data verdict below from one place; `asWritten: true` opts out, for the real-data probe, the two Lake landing measurements and Data Flow's Lake card, which describe `gigamon_ami` itself. A job's measured cost is filed under the query text that actually ran, dataset included, so a cost measured on the sample is measured again on real data. **KQL reminders live in the header comment** — e.g. use `count_distinct()`/`dcount()` not `dc()`, `sort by <col> desc`.
- `src/cribl/capi.ts` — one transport for every Cribl call that is *not* Search: `capi(method, path, body, init)` answers with `{ status, body }` rather than throwing, because its callers read the status as data (a 404 from provisioning means "not created yet"; a 404 from the KV store means "nobody has written this key"). Search keeps its own client on purpose — retry-on-429, cancellation and abort semantics are the product there, and bolting them onto a provisioning call would retry writes.
- `src/cribl/useSearch.ts` — the `useSearch(query, opts)` hook every tab uses. Re-runs when the query text, the global time range, the global refresh nonce, per-panel refetch, or `deps` change; aborts stale requests via `AbortController` + a request-id guard, and cancels the abandoned job server-side. **A hook that pins its own `earliest` opts out of the global range and of auto-refresh ticks** — only an explicit refresh re-runs it. Data Flow's 30-day tile, the most expensive query in the app, used to re-run on every range change that could not affect it. A panel may also name a scheduled search (`accel`), in which case the hook asks `src/cribl/accel/read.ts` for that schedule's stored result and only runs the query live when the read cannot answer — see **Acceleration** below. It also takes `deferred`, set by `useNearViewport()` in `src/components/nearViewport.ts` for a panel below the fold: concurrent jobs from one user are admitted ~1.6 s apart, so a tab firing six on mount does not start its sixth for ~8 s, and holding the below-the-fold ones back is the only lever on that. A deferred hook reports `loading`, never an empty result — `enabled: false` ("nothing is selected") and `deferred` ("not asked yet") are deliberately different states. Every submit from this hook also carries `set allow_previous_results` (see `search.ts`) unless the viewer asked for fresh data. **Two independent holds sit in front of the first submit**, and both report `loading`: *every* panel waits for the sample-data verdict (`datasetTarget.ts`, capped at `HOLD_DEADLINE_MS`, 4 s), and an accelerated one also waits for its mode and its saved search's serving verdict (`accel/serving.ts`, capped at `HYDRATE_DEADLINE_MS`, 2 s). The effect's key includes `target.dataset` and `servingEffect(...)` — what a verdict makes the read *do* — never the raw verdict, because `unknown` → `scheduled` changes nothing and re-running on it was a second billed job. `asWritten` passes through to `search.ts` for a figure that describes the customer's dataset. *(Added 2026-09-24, from `feat/sample-data-surfacing` and `fix/accel-paused-panels`.)*
- `src/cribl/inflight.ts` — a `useSyncExternalStore` counter of in-flight queries, incremented inside `runSearch`/`runFieldSummaries` (not in the hook), so the header spinner reflects *all* callers.
- `src/app/DashboardContext.tsx` — global `range` (time window) + `refreshNonce` + `manualRefreshNonce` + auto-refresh interval. `refresh()` bumps the nonces to re-run every query at once, and first re-checks the sample-data verdict (`recheckDatasetTarget()`) and re-reads the saved searches' serving verdicts (`refreshAccelServing()`) — both reads. An auto-refresh tick re-checks the sample-data verdict only while the app is on the sample, at most every `TICK_RECHECK_MS` (10 min), so a wall display switches back to real data by itself; it never re-reads the serving verdicts. Sub-minute refresh intervals are **not** offered; `WITHHELD_REFRESH_SECONDS` feeds the ⓘ that explains why.

**Query routing — Phase 8.1, built with nothing moved** (`src/cribl/routing/*`, `src/data/fieldTypes.ts`, `src/queries/routing.ts`; design: "Phase 8: reading gigamon_ami_pq", revision 2, on `docs/lake-acceleration-plan`). Owner decision 2026-09-25: Phase 8 Q1 is answered (a), Live-mode latency, so the router exists — but **no query reads `gigamon_ami_pq` in this release**, because no parity evidence exists (the Parquet dataset fills only from pack 0.2.1's HTTP source, unreleased). Routing is **per query, by exact text as written**, never per install. `routing/table.ts` `ROUTES` has one entry per query family (the design's §1.4 inventory; Capacity's talkers split per pivot): `{ id, from, queries, pin, target: 'json' | 'parquet', evidence }`, and **every entry is `json` with `evidence: null`**. `tableProblems()` — and `routing/table.test.ts` — fail an entry on Parquet without evidence (a report, a date, ≥3 windows at different UTC hours), a pinned one on Parquet, a text in two entries, and one whose text is not eligible under the type table; so moving a query is a data change backed by recorded evidence. Eligibility (`routing/eligibility.ts`) has three inputs: the text, read by `parity.ts` `classifyQuery` (grouped and piped queries; classes A, B, C and E found **anywhere** in an expression — `round(avg(x), 1)` is E — with a superset of `classify`'s patterns, and through every column the query made, so `extend r=x | summarize avg(r)` is E on `x`; plus **F** — a grouping on a raw field, including `by tolower(f)`, a key an `extend` made from `f`, and `| distinct f` — and **T** — a field typed `mixed`; **C is neutral**; APP_L4's `iif(isnotnull(x), x, "")` is neither A nor F, made by `extend` or named in the `by` clause) where A, B, E and T refuse; the **type table** `FIELD_TYPES` (empty until 8.0b's census — an unknown type refuses, and it is a frozen catalog); and **per-install density** (D/F only on a key present on every row; unmeasured today, `NO_DENSITY`). Pins are structural: `presence`, `evidence` and a new **`measurement`** (`queryTarget.ts` `PIN_WORDS`) for LANDING_LAG, REAL_DATA_PROBE, LAKE_HELD, PARTITION_CANDIDATES and the parity audits' own strings (those callers also submit `asWritten`). **At submit** (`search.ts` `executedQuery`): `asWritten` first, then the sample seam — while the app reads the sample, that is the only move and Parquet steps aside — then the installed router (`setQueryRouter`; `routing/route.ts` `decideRoute`), which also needs the window proven complete: `routing/completeness.ts` turns `COMPLETENESS_QUERY` (pack JSON vs Parquet `total.out_events`, labelled `cribl_lake:<packId>.<outputId>` as measured inside a pack; pipeline labels in a pack are unmeasured and unused) into per-5-minute-bucket verdicts cached for the page, refusing on a gap, a missing or `empty` bucket, one checked less than `COMPLETENESS_SETTLE_SECONDS` (360 s: the longest file-open time a destination here may carry, 300 s, plus the minute the schedules' `-3m` ends keep) after **it** ended — so a window ending "now" always refuses — or a window it cannot resolve — **nothing runs that query today**, so every window refuses. `main.tsx` installs the router by a **dynamic** import (a static one pulled ~16 kB of lazy tabs' queries into the first page load); before it lands every query runs as written. **Schedules stay on JSON (S1)**: a saved-search body is `accel/manifest.ts`'s, written with `capi`, and never passes the router (`table.test.ts` holds both). **The ⓘ** (`PanelInfo`) names the dataset the last live job of its query actually ran on, recorded when that job's results are read (`recordLanded`, called by `search.ts`), never at submit — a job in flight, failed or aborted leaves it naming the figure still on screen (`routing/ranOn.ts`; sample first; a stored-run-served figure names JSON), adds one line saying "Open in Search" opens the JSON archive when that was `_pq`, and keeps deep links and briefs on JSON. The display freeze holds the table as a `routing` section (`display-freeze.test.ts` also fails while any frozen entry is off JSON). `parity.ts` `compareGrouped` is grouped parity: top-N keys each side; a key in one top N and not the other fails unless it is tied at the rank-N boundary on either side (a tie excuses **only** a key's place in the top N); a key the other side does not hold at all fails, tied or not (absent and `""` are different keys, so class F fails); every key in either top N that both sides hold, tied keys included, has its figures held within `TOLERANCE`; and a pass needs one compared key outside a tie. *(Corrected 2026-09-25 after review: a tie on one side dropped the key from both, so a Parquet-only `""` group or a 50 % move behind a one-sided tie passed; `classifyQuery` read a wrapped aggregate and a derived key as class-free; the completeness check passed an open bucket checked in the same second; and the ⓘ was recorded at submit.)* **Not yet done**: running the completeness check (when, and its cost), reading density per install, filling `FIELD_TYPES`, the watchdog watching `gigamon_ami_pq`, and any parity evidence. *(Added 2026-09-25, `feat/phase8-1-router`.)*

- **Persistence:** go through `src/cribl/kv.ts` — never `localStorage`/`sessionStorage`/`IndexedDB`/cookies (unreliable in the sandbox, and never shared across users, devices or sessions). Documents are PUT as **`text/plain`**: given a JSON content type the store parses the body, persists the literal `[object Object]`, and still answers 200. Key shapes: `app/settings/<name>` install-wide, `<ns>/prefs/<userId>` per user, `<ns>/log/<epochMs>` append-only. `accel/state` is install-wide but deliberately *not* under `app/settings/` — a setting is a value a human chose and may edit; that document is the app's own record of its own writes, and it sits beside `accel/prefs/…` and `accel/log/…` so one `listKeys('accel/')` enumerates everything Phase 2 stored. One writer per document — `prefs.ts` rewrites its whole document on every flag change, so a second writer's field would be dropped. Guided Setup's commit memory (`guided_setup_memory/commits`, group → key → `{hash, message}`) also holds the onboarding pack's last commit under `onboarding_pack`; the stranded-commit repair deploys only hashes found there. - **UI:** use the Capra design system (`@capra/core`, `@capra/icons`, `@capra/theme`). In CSS reference design tokens via the `token()` function, never raw CSS variables — and check what a token resolves to: `border.default` is the *shorthand* `1px solid var(…)`, not a colour, which is why 55 sites once shipped `1px solid 1px solid #cdced6` — invalid at computed-value time, so `border-style` computed to `none` and the app rendered **no borders at all**. Use `--gm-border`, which is `color.border.neutral.default`. Spacing and font sizes come from the `--gm-sp-*` / `--gm-fs-*` scales at the top of `src/App.css`; a bare px in a padding, margin, gap or font-size is a missing *step*, not a shortcut — add the step, with a line saying what forced it. Don't attach classes to Capra components or depend on their internals; do spacing with wrappers. Capra's `Modal` gives you the role, the label, the portal, the `inert` app root and Escape — it does **not** give you initial focus or `aria-describedby`; `<ConfirmDialog>` supplies both, so build on it rather than on `Modal` directly.
